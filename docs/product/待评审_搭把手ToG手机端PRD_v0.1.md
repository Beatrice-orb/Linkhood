## 先看这里｜30 秒审阅版

1. **手机端定位**：社区工作人员的移动执行工作台，处理“今天要做什么、现场下一步是什么、哪些 AI 草稿需要我确认”。
2. **P0 页面**：`今日工作台`、`走访记录核对`；活动签到作为工作台二级流程，不先建设完整移动后台。
3. **与电脑端分工**：手机端负责现场、走访和轻核对；电脑端负责完整供给接入、活动配置、档案管理和需求分析。
4. **AI 原则**：AI 只做抽取、转写、分类和草稿；发布、入档、专业判断与处置必须由工作人员确认。
5. **安全原则**：Demo 只用模拟居民与授权记录，不展示真实姓名、门牌号、手机号或真实个案。

本次最希望团队 Review：手机端 P0 范围、手机是否具有最终发布/入档权，以及与居民端、电脑端共享哪些对象和状态。

## 1. 背景与目标

“搭把手”是以社区为入口的公共服务连接与运营协作平台：让分散在社区、街镇、政府部门、公共机构、企事业单位和社会组织中的服务，更容易被居民找到、理解和使用；正式服务覆盖不到的低风险生活小事，再由可信邻里互相搭把手。

ToG 手机端不复制电脑后台，也不做传统社区管理系统的缩小版。它服务工作人员离开工位后的真实场景：活动现场、入户走访、服务点核验和临时跟进。

### 1.1 v0.1 目标

- 让工作人员在 10 秒内看见今天最需要行动的事项。
- 让活动、公共服务和走访记录在手机端完成最小现场动作。
- 展示 AI 如何减少整理工作，同时保留清晰的人审节点。
- 与电脑端、居民端通过同一套对象 ID 和状态事件联动。

### 1.2 本阶段不解决

- 完整公共服务库维护与批量发布。
- 跨周期数据分析和领导驾驶舱。
- 完整社工个案管理系统。
- 真实居民数据库、真实录音存储和复杂组织权限。
- 自动审批、自动发布、自动入档或自动分配稀缺资源。

## 2. 用户角色与典型场景

| 角色 | 核心任务 | 典型环境 |
|---|---|---|
| 社区工作人员 | 活动执行、服务核验、咨询分流 | 社区站点、活动现场、移动途中 |
| 专业社工 | 走访记录、需求评估、跟进计划 | 入户走访、电话回访、服务站 |
| 活动执行人员 | 报名确认、签到、候补与异常处理 | 活动现场 |
| 社区运营负责人 | 查看紧急事项、分派和确认 | 手机临时处理，电脑集中管理 |

核心场景：

1. 上班后查看当天活动、待核对服务和居民跟进。
2. 活动开始前进入签到，处理名单和现场变化。
3. 核对一条从公众号通知抽取出的公共服务草稿。
4. 完成走访后，用语音或文字形成结构化记录草稿。
5. 核对含糊表述，保存草稿或提交负责人审核。
6. 收到需求热点提醒后，在电脑端继续查看证据。

## 3. 手机端与电脑端分工

| ToG 工作 | 手机端 | 电脑端 |
|---|---|---|
| 公共服务对接 | 查看来源、补充现场信息、提交核对 | 来源接入、完整编辑、审核发布、到期复核 |
| 活动运营 | 今日活动、签到、现场异常、临时通知草稿 | 创建、排期、报名漏斗、触达与复盘 |
| 社工档案 | 授权、录音/文字、AI 草稿、人工核对 | 档案检索、时间线、权限、审计与跟进 |
| 需求热点 | 轻量提醒、标记关注 | 聚合证据、供给缺口判断、补位方案 |

原则：手机端只保留“现场可完成”的动作，不把桌面后台等比例缩小。

4. 需求热点提醒。
5. 已完成事项。

## 5. 页面一｜今日工作台

### 5.1 页面目标

让工作人员快速回答：今天要做什么、哪件最急、下一步是什么、哪些是 AI 草稿。

### 5.2 页面结构

#### A. 身份与服务范围

- 产品：`搭把手 · 社区工作台`
- 当前范围：`西红门社区`
- 日期：`7 月 11 日 周六`
- 当前用户：`李老师`
- 角色：`社区工作人员`或`专业社工`

#### B. 今日摘要

示例：

> 今天有 2 场活动、3 条供给待核对、1 次居民跟进。

摘要必须由具体任务汇总，不显示无法解释的活跃度或治理指数。

#### C. 今日重点活动

- 活动：银龄反诈小课堂（演示数据）
- 时间：14:00
- 地点：西红门党群服务中心
- 报名：38 / 50
- 状态：即将开始
- 主操作：`现场签到`
- 次操作：`查看详情`

异常状态：满额、候补、地点待确认、延期、取消、签到异常。

#### D. 待核对公共服务

- 服务：西红门医院 2026 年三伏贴服务
- 来源：官方公众号
- AI 状态：已提取字段，存在待确认项
- 待确认：价格、每日容量、服务站具体时段
- 操作：`查看原文`、`继续核对`

手机端默认提交核对结果，不直接承诺实时余量或自动发布。

#### E. 居民跟进

- 对象：居民 A017（模拟档案）
- 事项：走访记录待核对
- 状态：AI 草稿
- 待处理：含糊表述、后续跟进
- 操作：`继续记录`

卡片不展示完整地址、身份证号、手机号或与当前任务无关的敏感信息。

#### F. 需求热点提醒

v0.1 只显示轻量提醒：

> 暑期托管需求连续两周上升（演示数据）
>
> 31 条脱敏信号，当前仅找到 1 项已核验供给。

操作：`标记关注`、`电脑端查看证据`。

#### G. AI 边界提示

固定提示：

> AI 只整理草稿，发布、入档与处置均由你确认。

### 5.3 核心交互

- 点击任务进入对应处理页。
- 完成后进入“已完成”，首页摘要同步变化。
- 低置信度、字段冲突和敏感信息必须提示人工核对。
- 无网络可保存本地草稿，但不能显示发布或入档成功。
- 权限不足时隐藏敏感正文，并提示转交负责人。

### 5.4 页面状态

| 状态 | 处理方式 |
|---|---|
| 加载中 | 骨架屏，不先显示虚假数字 |
| 今日无任务 | 引导查看近期活动或待核对服务 |
| 数据过期 | 显示最后同步时间和重新同步 |
| 网络异常 | 允许本地草稿，禁止提交/入档 |
| 权限不足 | 隐藏敏感信息，允许转交 |
| 高风险事项 | 停止 AI 建议，转人工或专业机构 |

## 6. 页面二｜走访记录核对

### 6.1 页面目标

把一次经授权的录音或文字笔记整理成可核对的记录草稿，减少重复整理时间，但不替代社工专业判断。

### 6.2 使用前提

开始记录前必须确认：

- 已向居民说明记录用途。
- 已获得本次录音与记录授权。
- 居民可拒绝录音并改为手动记录。
- 未确认授权时不能启动录音。

### 6.3 页面结构

#### A. 对象与授权

- 对象：居民 A017（模拟档案）
- 记录类型：入户走访
- 记录人：李老师
- 时间：2026-07-11 10:30
- 授权状态：已获得本次记录授权
- 可见范围：仅当前服务团队

#### B. 原始材料

- 录音文件与时间轴
- 转写文本
- 手动文字
- 操作：回听、查看转写、重新录入

真实照片上传和长期录音存储不属于 v0.1。

#### C. AI 结构化草稿

AI 必须把内容分为：

1. **客观事实**：发生了什么。
2. **居民原话**：保留原意，不升级成医学或风险结论。
3. **已表达需求**：居民明确提出的服务诉求。
4. **社工判断**：默认待社工填写或确认。
5. **后续跟进**：事项、负责人、时间。

#### D. 待核对提示

示例：

- “‘最近’需要补充具体时间。”
- “‘偶尔头晕’只能保留为居民原话，不能自动转换为诊断。”

每项支持：修改、删除、暂不确认、回听对应音频。

#### E. 底部操作

- `继续编辑`
- `保存为草稿`
- `提交负责人审核`或`确认并入档`（取决于权限）

提交前二次确认：

> 只有你确认过的内容会进入专业服务档案。

### 6.4 AI 输出要求

- 不补写原始材料中没有的信息。
- 每段结构化内容保留原文或录音时间戳。
- 低置信度内容显式标记。
- AI 失败时保留原始记录，允许手动整理。
- 不读取居民端聊天、邻里动态或普通浏览行为生成档案。

## 7. 核心流程

### 7.1 活动现场

`工作台 → 活动详情 → 报名情况 → 现场签到 → 处理异常 → 同步电脑端`

候补转正式、临时加容量、延期/取消、照片授权必须人工确认。

### 7.2 服务核对

`电脑端创建服务草稿 → 手机收到核对任务 → 查看来源 → 补充现场信息 → 提交核对 → 电脑端确认发布`

手机端不自动判断资格、承诺余量、分配名额或代表机构承诺。

### 7.3 走访记录

`确认授权 → 录音/文字 → AI 转写与结构化 → 标记含糊内容 → 人工核对 → 草稿/审核/入档 → 生成跟进任务`

### 7.4 热点提醒

`居民行为形成脱敏信号 → 电脑端聚合 → 手机收到提醒 → 标记关注 → 电脑端核验证据与补位`

## 8. 核心对象与状态

### 8.1 对象

| 对象 | 最小字段 |
|---|---|
| `WorkTask` | id、类型、标题、负责人、截止时间、优先级、状态、关联对象、是否 AI 草稿 |
| `PublicServiceCard` | 名称、供给方、对象、资格、时间、地点、报名方式、来源、核验状态、可用状态、缺失字段、最后核验时间 |
| `CommunityActivity` | 主办方、时间、地点、容量、报名/候补/签到数、阶段、照片授权 |
| `VisitRecord` | 授权、原始材料、事实、原话、需求、社工判断、跟进、含糊项、入档状态 |
| `DemandTopic` | 主题、周期、去重信号量、证据类型、供给数量、趋势、处理状态 |

本 PRD **不要求立即改动居民端现有 `Service` 类型**。开发时先在 ToG 模块使用 `PublicServiceCard`，再通过适配层映射为居民端展示字段，避免 PRD 先锁死队友尚未定稿的数据模型。

### 8.2 状态

- 工作任务：`待处理 → 处理中 → 待人工确认 → 已完成`
- 走访记录：`记录中 → AI 草稿 → 待核对 → 待审核/已入档`
- 活动现场：`报名中 → 即将开始 → 签到中 → 进行中 → 已结束`
- 服务核验：`AI 草稿 → 待核验 → 已核验 → 待发布 → 已发布`

内容更新后必须重新进入待核验，不能沿用旧核验状态。

## 10. AI、人审与权限

### AI 可以做

- 从文章和通知中抽取字段、提示缺失和冲突。
- 把录音转写并拆分为事实、原话、需求和跟进。
- 生成提醒、总结和通知草稿。
- 对脱敏聚合信号进行主题归类。

### 必须由人确认

- 公共服务发布和状态确认。
- 活动延期、取消、候补转正和容量变化。
- 社工记录入档、专业判断和转介。
- 资源分配与任何对外承诺。

### 禁止

- 自动资格审批、自动发布、自动入档。
- 居民信用分、风险分和黑箱画像。
- 从聊天或兴趣推断健康、经济或家庭状况。
- 未经核实的医疗、法律和政策结论。

### 权限与隐私

- 最小必要、按角色和任务授权。
- 活动执行人员不能查看专业社工档案。
- 社工档案与普通产品数据隔离。
- 查看、修改、提交和导出保留审计记录。
- Demo 只用模拟居民和模拟记录。
- 需求热点只使用脱敏聚合数据；小样本不展示。

## 12. 优先级

### P0｜初版 Demo

- 今日工作台。

- 公共服务待核对卡与原始来源。
- 走访记录核对。
- AI 草稿、含糊项与人工确认。

- 独立服务活动列表。

- 390×844 视口无横向溢出，首屏可见活动、服务核对和居民跟进。

## 14. 待团队 Review

1. P0 是否只保留“工作台 + 走访核对”，其余作为二级入口？
2. 手机端是否可以最终发布服务，还是只能提交电脑端审核？
