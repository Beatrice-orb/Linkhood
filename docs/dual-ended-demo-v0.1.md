# 搭把手双端联动 Demo v0.1

## 1. 这版已经做成什么

本版把原居民端代码、ToG 端视觉 Demo、ToG PRD 与真实公共服务样例收敛为一条可操作的最小闭环：

`公开来源 → AI 可核对草稿 → 工作人员确认 → 居民服务卡 → 居民表达办理意向 → 社区端脱敏回流`

两端共享同一套 `PublicServiceCard` 与 `ResidentActionEvent` 契约。Demo 使用同一浏览器的 `localStorage` 串联状态，不依赖后端，也不会产生真实发布、报名、通知或居民入档。

## 2. 本轮开发步骤

1. 盘点原居民端已有交互、ToG 五张视觉稿、两端 PRD 和真实服务数据，明确冲突与可复用部分。
2. 冻结 v0.1 主故事与共享数据契约，区分真实公开来源、演示工作流和纯演示运营数据。
3. 建立多入口路由与共享演示状态，保证电脑端发布后居民端能读取同一服务卡。
4. 开发社区运营电脑端：来源预览、AI 字段提取、核心字段人工确认、未知字段逐项确认、发布门禁。
5. 开发居民端：公开服务列表、详情、适用对象、状态、来源原文、办理意向与“我的进度”。
6. 开发回流页：只传脱敏行动信号；不足 5 个去重主体时不升级为需求热点。
7. 开发社区工作手机端：今日任务、走访草稿保存、提交负责人审核；提交后转为只读。
8. 完成响应式、主交互、状态持久化、隐私边界、控制台与构建 QA。

## 3. 最小场景闭环怎么演示

### 路演版：90 秒

1. **0—25 秒**：电脑端打开西红门医院真实通知，点“生成可核对草稿”；强调 AI 只抽取与提示缺项。
2. **25—45 秒**：快速确认核心字段和 3 个未知字段表达，点“确认并发布”；强调未知不补造、关键动作由人确认。
3. **45—70 秒**：进入居民端，打开三伏贴服务卡，露出来源、对象、状态和“余量请确认”，点“我想办理”。
4. **70—85 秒**：进入社区端反馈页，展示 1 条脱敏办理意向；不足 5 个去重主体，不升级为热点。
5. **85—90 秒**：扫一眼首页低风险“借工具”侧卡，收束品牌双重含义：正式服务优先，可信邻里只补位生活小事。

### 完整讲解版：4 分钟

演示前打开 `#/demo`，点击“重置演示”。

#### 0:00—1:30 社区端接入真实服务

1. 进入“社区运营电脑端”。
2. 展示左侧西红门医院公众号来源与原始通知快照。
3. 点击“生成可核对草稿”。
4. 强调 AI 只做结构化整理，不自动发布。
5. 点击“逐项对照原文并确认必要字段”，再确认价格、每日容量、各服务站时段三项未知字段。
6. 点击“确认并发布”。

关键讲法：已知字段必须人工核对；未知字段不补造答案，而是原样告诉居民。

#### 1:30—2:50 居民端找到并判断服务

1. 点击“在居民端预览”。
2. 搜索“帮爸妈找附近的三伏贴服务”。
3. 打开服务卡，查看时间、地点、适用对象、办理方式与官方原文。
4. 点击“我想办理”。

关键讲法：这个按钮只表达办理意向，不等于报名成功，也不代替官方预登记。

#### 2:50—3:40 社区端收到脱敏回流

1. 点击“查看社区端演示回流”。
2. 展示“1 条脱敏居民办理意向”。
3. 展示阈值判断：少于 5 个去重主体，只记为行动信号，不包装成需求热点。

关键讲法：社区看到的是服务补位信号，不是可反查个人的画像或档案正文。

#### 3:40—4:00 可选补充

进入社区工作手机端，打开走访记录，说明“AI 草稿 → 人工核对 → 提交负责人审核”的第二条治理边界。这个流程是辅助证明，不抢占主闭环叙事。

## 4. Demo 边界

- 三伏贴、暑期研学营、招聘活动来自真实公开来源快照；演示前仍需再次核验状态。
- 页面明确声明：公开来源不代表来源机构与项目存在合作关系。
- 活动运营、走访对象、报名数字和工作人员账号为演示数据。
- “我想办理”只写入本地匿名演示事件，不执行真实报名、通知或入档。
- 当前两端联动只在同一浏览器内成立；没有后端、账号体系、跨设备同步或真实权限控制。
- 旧居民端中涉及房号、信用分、聊天和个人模拟档案的入口不对外暴露。

| 4 | Bera / integrator | 提交本地实现、推送独立分支并开 Draft PR | 代码 commit、Draft PR、净变更说明 | 不混入 PR #1/#2/#3，CI/构建通过 |

### P1：可测试产品版

1. 后端服务卡、来源、审核、发布、匿名事件 API。
2. 工作人员登录、角色权限、审核日志与撤回/过期机制。
3. 真实来源导入：链接、图片/OCR、字段抽取、重复检测和状态复核任务。
4. 居民端真实搜索、筛选、收藏、办理跳转与状态更新。
5. 去重、阈值、数据保留期限、用途限制和审计策略。
6. 走访授权、草稿版本、负责人审核与最小必要字段。

### P2：单社区试点版

1. 只选 1 个社区、3—5 个稳定公共服务来源和 1 个工作人员团队。
2. 建立来源新鲜度 SLA、人工复核责任人与服务下架流程。
3. 用“找到有效服务的比例、来源核验耗时、居民行动转化、错误信息率”评估价值。
4. 低风险邻里互助继续作为侧线，不在公共服务闭环稳定前扩成社交平台。

## 6. 需要产品团队具体讨论的地方

| 议题 | 本版暂定 | 需要拍板的问题 |
|---|---|---|
| 产品主叙事 | 公共服务抵达是主线，低风险互助是侧线 | 黑客松最终是否只讲一条主故事 |
| 居民主 CTA | “我想办理”=表达意向 | 何时才可叫“报名/预约成功”，是否跳转官方渠道 |
| 服务范围 | 西红门优先，大兴区级资源补充 | 区级服务如何提示距离与适用范围 |
| 人工发布门禁 | 核心字段 + 未知字段表达全部确认 | 哪些字段绝对阻断发布，核验有效期多长 |
| 数据新鲜度 | 每条服务显示来源和最后核验时间 | 到期自动下架、提醒复核还是降级展示 |
| 需求热点 | 至少 5 个去重主体才进入候选 | 阈值是否按主题、时间窗和社区分别设定 |
| 居民数据 | 只回传匿名行动事件 | 去重方式、保留期、撤回权和可见角色 |
| ToG 手机端 | 今日工作台与走访核对为辅助流程 | 黑客松是否保留走访演示，避免主线过散 |
| 活动运营 | 作为视觉与能力补充 | 是否进入 v0.1 交付，还是留到 v0.2 |
| 来源关系表述 | 明确“公开来源不代表合作” | 若后续接入机构，如何显示授权/合作状态 |
| AI Agent 形态 | v0.1 使用确定性草稿结果 | 后续是单 Agent、嵌入式能力还是多 Agent；错误由谁复核与负责 |
| 首个 ToG 共建 owner | 暂用社区运营角色演示 | 镇、社区、医院或社会组织谁维护来源、谁有发布权 |
| 邻里互助信任机制 | 只保留借工具低风险侧卡 | 社区身份核验粒度、举报、完成确认与高风险拦截如何落地 |
| 居民服务档案 | 当前不进入公开居民端 | 下一版是否做本人可控档案；与授权社工个案如何物理隔离 |
