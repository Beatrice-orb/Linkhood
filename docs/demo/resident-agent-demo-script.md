# 居民答疑 Agent → 社区匿名需求信号｜90 秒演示脚本

> 演示目标：证明居民可以得到有来源的社区答疑；当现有供给未覆盖追问时，系统内部自动形成匿名需求信号，并在社区电脑端成为居民声音。
> 全部问答、活动、科室、电话和需求信号均为演示数据。

## 1. 演示前准备

- ToC 基线：`main@3e3b604`。
- ToG subtree 来源：`main@7160abc`。
- 打开同一 Preview 域名的两个标签页：居民端和社区电脑端。
- 将居民端视口设为约 390×844，社区端视口设为约 1440×900。
- 重置匿名需求演示仓库，确认社区端尚无本轮新增信号。
- 确认真模型可用；同时确认无 Key 或超时时确定性回退可完成相同脚本。
- 所有模拟电话均显示“模拟号码，不可拨打”。

## 2. 主演示

### 0–10 秒｜进入居民答疑

画面：居民端当前主页，点击右下角 AI 助手。

旁白：

> 居民可以直接询问社区服务和活动。AI 只依据当前社区资料回答，不把模型常识当成社区事实。

### 10–28 秒｜回答已有供给

居民输入：

> 社区最近有没有适合下班后参加的活动？

预期回答要点：

- 展示已有青年夜校或同类模拟活动。
- 说明时间、地点和参与方式。
- 展示模拟来源与最后核验时间。
- 不显示需求提交入口，也不生成匿名信号。

旁白：

> 已有供给可以直接回答，并带来源和核验时间。

### 28–50 秒｜追问当前未覆盖需求

居民追问：

> 我更想学 AI，有没有工作日晚上的 AI 入门课？

预期回答：

> 在当前已核验的演示资料中，暂未找到工作日晚间的 AI 入门活动。你可以联系社区活动运营岗了解后续安排：010-0000-1024（模拟号码，不可拨打）。

画面必须满足：

- 不出现“是否帮你提交”。
- 不出现联系方式输入框。
- 不出现“已记录”“提交成功”“已受理”或处理进度。
- 不承诺社区会新增活动或联系居民。

旁白：

> AI 不假装社区一定有，也不替居民创建工单。居民只看到真实的知识边界和可咨询方向。

### 50–78 秒｜切到社区电脑端

切换到社区电脑端“居民声音 / 需求洞察”。

新增信号显示：

- `居民希望社区增加工作日晚间的 AI 入门活动`
- `匿名需求信号 · 非工单 · 演示数据`
- 居民声音：`有没有工作日晚上的 AI 入门课`
- 情境标签：`工作日晚间`、`数字技能`
- 供给缺口：当前活动资料没有对应课程
- 建议承接：社区活动运营岗
- 信号次数：1

旁白：

> 对社区端来说，这个未被现有供给覆盖的方向会自动形成匿名需求信号。这里只保留需求内容，不包含姓名、电话、房号或居民档案，也不代表正式受理。

### 78–90 秒｜收口

旁白：

> 单条信号先作为居民声音供运营人员理解；累计信号可以帮助社区判断服务和活动缺口。正式回应、项目创建和资源安排仍由工作人员确认。

## 3. 社区端画面检查

- 新信号排在列表顶部或有清晰的“新信号”视觉提示。
- “非工单”与“演示数据”无需进入详情即可看见。
- 不展示居民头像、姓名、电话、楼栋、房号、信用分或画像编号。
- 不出现“待受理”“待回复”“24 小时 SLA”等工单式文案。
- 若同一居民会话重复追问，仍只显示一条信号，`信号次数`递增。

## 4. 回退演示

真模型不可用时：

1. 居民输入保持不变。
2. 系统在限定超时后使用确定性回答。
3. 回答文本、来源结构、科室路由和匿名信号契约保持一致。
4. 不向居民显示 API 错误、Key 状态或匿名写入状态。

演示者可在开发调试区域确认 `fallback`，但该标识不进入居民主界面。

## 5. 可替换服务场景

如活动数据尚未定稿，可使用服务场景：

1. 居民问：“社区有老年助餐点吗？”
2. AI 回答已有助餐点和咨询方式。
3. 居民追问：“能不能每天送餐上门？”
4. AI 说明资料中没有送餐上门信息，并展示模拟承接科室。
5. 社区端新增“助餐送餐上门”匿名服务需求信号。

同样不得询问提交、采集电话或展示受理成功。

## 6. 演示通过标准

- 已有供给回答有来源，未补造余量或资格。
- 未覆盖需求自动进入社区端，无居民提交动作。
- 居民端全程看不到匿名记录或受理结果。
- 社区端信号不含 PII，并明确“匿名、非工单、演示数据”。
- 同一主题重复追问不产生重复信号。
- 真模型和确定性回退均能在 90 秒内完成主链。
